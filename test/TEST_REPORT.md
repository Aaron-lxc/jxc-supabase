## 三、发现的缺陷与修复 🔴→✅

### P0：报损单 / 报溢单不同步（数据持久化漏洞）

- **现象**：`sync.js` 的 `diff / snapshot / push` 仅遍历 `sync.COLLS` 中的集合；而 `losses`、`overflows` 不在 `sync.COLLS` 中。后果——新建 / 修改 / 删除报损报溢单**永远不会被行级同步推送到 Supabase**（虽 `loadAll` 全量拉取，但 diff 不扫描它们，本地改动永不回传）。这是「看似能增删改查、实则不同步」的假闭环。
- **修复**：`sync.COLLS` 增补 `'losses'`、`'overflows'`。
- **验证**：集合三处登记现为 **41 = 41 = 41** 完全一致（`test/check-collections.cjs`）。

### 铁律一致性：compute-core 漏登 3 个集合

- `compute-core.emptyDB` 原缺 `losses`、`overflows`、`transfers`，违反「store.emptyDB / sync.COLLS / compute-core.emptyDB 三处登记」铁律（compute-core 为只读统计，不直接影响同步，但属规范缺失）。
- **修复**：补齐 `losses`、`overflows`、`transfers`。

## 四、风险项（建议优化，非阻断）

### R1：预存货款抵扣余额不足时「部分扣减且不回滚」—— ✅ 已修复（2026-09-14）

- **根因**：原 `applyPrepaidDeduct` 在余额不足时会「边遍历边扣 `usedAmount`，扣光可用余额后才返回 `{ok:false}`」，非原子。
  `confirmSettle` 的回滚逻辑（release 旧值 → apply 新值失败 → 再 apply 旧值还原）在余额已被部分占用的状态下，
  「还原旧值」会因余额耗尽而失败，导致 `usedAmount` 永久多扣（= 已扣光可用余额），而销售单仍记录旧 `prepaidDeduct`，即**预存货款被误扣、余额错乱**。
- **修复**：`applyPrepaidDeduct` 改为**先核算总可用余额，不足则直接返回 `{ok:false}` 且不改动任何 `usedAmount`**（`store.js`）；
  余额充足才执行 FIFO 扣减。调用方回滚（再 apply 旧值）因此总能成功还原。
- **回归测试**：新增 B4 用例（B18–B21）模拟「改单扣超额 → 原子失败不改动 → 回滚还原旧值」，断言余额无残留、无多扣。本项已闭环。

### R2：统计全量遍历

- `dashboard` / `report` 的 `stats()` 每次渲染全量遍历所有集合（O(数据量)）。中等数据量（数千条）无感；若单账套 > 1 万条，建议在常用页加缓存 / 索引。
- **已确认渲染路径（列表行）无 O(n²)**：`coopTime` / `completedSalesIn` 仅在表单 computed 与统计函数中调用，不在列表行循环内。
